## What system/approach is used

The backend uses **Pino** as the structured logging engine, wired into NestJS through the `nestjs-pino` integration (`LoggerModule`). Both the API and Engine services bootstrap with `NestFactory.create(..., { bufferLogs: true })` and then call `app.useLogger(app.get(Logger))`, which replaces Nest's default logger with Pino so that every controller/service log goes through the same pipeline.

HTTP request/response logs are produced automatically by `pino-http` (via `nestjs-pino`'s `LoggerModule.forRootAsync`) — there is no per-request middleware written in application code. The module reads configuration from Nest's `ConfigService`, which is backed by a Zod-validated environment schema.

## Key files and packages

- `backend/libs/shared/src/logging/logging.module.ts` — single shared NestJS module that registers `LoggerModule.forRootAsync` with pino-http options.
- `backend/apps/api/src/main.ts` — API entrypoint; injects the shared `Logger` into Nest's DI container.
- `backend/apps/engine/src/main.ts` — Engine entrypoint; same pattern for WebSocket-capable service.
- `backend/libs/shared/src/config/env.schema.ts` — declares `LOG_LEVEL` as a validated enum of `["fatal", "error", "warn", "info", "debug", "trace"]`, defaulting to `info`.
- `backend/libs/shared/src/platform.module.ts` — re-exports `LoggingModule` so feature modules can import it.

## Architecture and conventions

### Bootstrap
Each Nest app creates its factory with `{ bufferLogs: true }` so logs emitted during module initialization are buffered until the transport is ready, then calls `app.useLogger(app.get(Logger))`. This ensures both the API and Engine share the same Pino instance and log format.

### Request correlation
Every incoming HTTP request gets a stable `req.id` generated by `genReqId`: it first checks the `x-request-id` header (allowing callers to propagate a trace id) and falls back to `crypto.randomUUID()`. All subsequent structured logs include this id, enabling cross-service tracing between the API and Engine when they communicate over Redis/queues.

### Sensitive data redaction
The pino-http `redact` config explicitly masks sensitive fields:
- `req.headers.authorization`
- `req.headers.cookie`
- `req.body.password`
- `req.body.otp`
- `req.body.token`
All redacted values are replaced with the literal string `[REDACTED]`.

### Health endpoint exclusion
Automatic HTTP logging ignores `/health` requests via `autoLogging.ignore`, preventing noise from liveness probes.

### Log level strategy
Log level is read from the `LOG_LEVEL` environment variable at boot time, validated by Zod against the five standard Pino levels plus `fatal`. The default is `info`. Application code uses the injected `this.logger` (a Nest `Logger` instance backed by Pino) with methods like `debug`, `warn`, `error`; there is no custom wrapper around these calls — consumers use the standard Nest logger API.

### Structured fields
Because Pino is configured via `pinoHttp`, every HTTP log line is JSON-structured and includes at minimum: `level`, `msg`, `req` (with method/url), `res` (status), `responseTime`, and the correlated `req.id`. Business logs emitted via `this.logger.info/warn/error(...)` are appended to the same stream and inherit the current context.

### Sinks
There is no file or external sink configured in this repository — Pino writes to stdout/stderr by default. Production deployment is behind Nginx/Docker Compose, so logs are collected by the container runtime / orchestrator (e.g., Docker logs, cloud log driver). No log rotation or aggregation library is present in the codebase.

## Conventions and constraints

1. **Do not instantiate your own logger.** Every module imports `Logger` from `@nestjs/common` (provided by `nestjs-pino`) via constructor injection; no `new Logger()` calls were found.
2. **Use Nest logger methods only.** Callers invoke `this.logger.debug/info/warn/error/fatal(message)` — no direct `console.log` for operational output was observed in business modules.
3. **Never log secrets in plain text.** The redaction policy enforces masking of authorization headers, cookies, passwords, OTPs, and tokens at the HTTP layer; application-level loggers should avoid including such values in message strings.
4. **Propagate correlation ids via `x-request-id`.** If a caller supplies an `x-request-id` header, it will be preserved across the request lifecycle; otherwise one is auto-generated.
5. **Health probes are silent.** Requests to `/health` are excluded from automatic HTTP logging, so health-check endpoints do not pollute logs.
6. **Log level is environment-driven.** Changing `LOG_LEVEL` in `.env` (or the container environment) is the supported way to adjust verbosity; there is no runtime toggle.
